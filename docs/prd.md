## 1. ภาพรวมและเป้าหมาย

### 1.1 ปัญหา ⚠️ S-01 (ต้องยืนยันกับสนาม pilot)
- **ผู้เล่น:** ต้องทัก LINE หรือโทรหาสนามทีละแห่งเพื่อถามว่าคอร์ทว่างไหม ไม่เห็นราคาและตารางล่วงหน้า และรอสนามตอบนาน
- **สนาม:** จัดตารางด้วยสมุด, LINE หรือ Excel ทำให้เกิดการจองซ้อน ต้องตรวจสลิปด้วยมือ และสรุปรายได้หรือทำเอกสารภาษีได้ยาก

### 1.2 เป้าหมาย
- **G1:** ผู้เล่นหาคอร์ทว่างและจองเสร็จได้เองโดยไม่ต้องทักสนาม
- **G2:** สนามลดงานจัดตาราง ตรวจสลิป และทำเอกสารภาษี
- **G3:** Platform มีรายได้จากค่าคอมมิชชัน และขยายไปสนามอื่นได้

### 1.3 ตัวชี้วัดความสำเร็จ (วัดช่วง pilot M4) ⚠️ S-02
| ตัวชี้วัด | เป้าหมาย | วัดจาก |
|---|---|---|
| สนามที่ใช้งานจริง | 5 สนาม | จำนวนสนาม `Approved` ที่มีการจองทุกสัปดาห์ |
| สัดส่วนชั่วโมงที่ขายได้ซึ่งบันทึกในระบบ (ออนไลน์ + walk-in) | ≥ 70% | เทียบกับยอดที่สนามแจ้ง |
| เวลาตั้งแต่เปิดหน้าสนามจนอัปโหลดสลิป (median) | ≤ 3 นาที | `venue_page_viewed` → `slip_uploaded` |
| เวลาตั้งแต่อัปโหลดสลิปจนสนามตรวจเสร็จ (median) | ≤ 15 นาที | `slip_uploaded` → `booking_confirmed` / `booking_rejected` |
| การจองซ้อน | 0 ครั้ง | |
| เอกสารภาษีที่ต้องยกเลิกเพราะระบบคำนวณหรือออกผิด | 0 ฉบับ | |

## 2. ผู้ใช้และบทบาท
| บทบาท | คือใคร | ทำอะไรในระบบ |
|---|---|---|
| **Booker** (ผู้จอง) | ผู้เล่นแบดมินตันทั่วไป | ค้นหาสนาม, จอง, จ่ายเงินและอัปโหลดสลิป, ยกเลิก, ดูประวัติ, ขอใบกำกับภาษีเต็มรูป |
| **Venue Owner** (เจ้าของสนาม) | ผู้สมัครสนามเข้า platform | มีทุกสิทธิ์ของสนามตัวเอง รวมถึงสิทธิ์ที่เป็นของ Owner เท่านั้น (ตาราง US-14) |
| **Venue Staff** (พนักงานสนาม) | ผู้ที่ Owner เชิญเข้าระบบ | ทำได้ตามสิทธิ์ที่ได้รับ (ตาราง US-14) |
| **Platform Admin** | ผู้ดูแล platform (เจ้าของโปรเจกต์) | อนุมัติหรือระงับสนามและผู้ใช้, ตั้งอัตราคอมมิชชัน, ตรวจการชำระค่าคอมมิชชัน, ดูภาพรวม, จัดการเรื่องร้องเรียน |

**กฎบัญชีผู้ใช้**
- ผู้ใช้หนึ่งบัญชีมีได้หลายบทบาท และเป็น Staff ได้หลายสนาม
- หนึ่งสนามมี Owner ได้ 1 บัญชี ส่วน Owner หนึ่งบัญชีมีได้หลายสนาม ⚠️ S-20
- ผู้ที่ทำงานกับหลายสนามต้องเลือก "สนามที่กำลังจัดการ" ก่อนทุกครั้ง ระบบจะแสดงข้อมูลเฉพาะสนามนั้นและไม่มีมุมมองรวมหลายสนาม ยกเว้น Platform Admin
- ข้อมูลของแต่ละสนามต้องแยกจากกันเด็ดขาด (หัวข้อ 8)

## 5. User Stories และ Acceptance Criteria (MVP)

### 5.0 โมเดลการจอง (ใช้กับทุก story)
- **การจอง (Booking)** 1 รายการ = ช่องเวลา (BookingSlot) 1 ช่องขึ้นไปในสนามเดียว มีสถานะเดียว, QR เดียว และสลิปเดียว
- ยกเลิกได้ทั้งการจองเท่านั้น **ไม่มีการยกเลิกบางช่อง** ⚠️ S-21
- "เวลาเริ่มเล่น" = เวลาเริ่มของช่องแรกสุด · "เวลาจบ" = เวลาจบของช่องสุดท้าย
- ช่องทางการจอง: `Online` (ผู้จองสร้างเอง) หรือ `Staff` (พนักงานสร้างให้ลูกค้า ทั้ง walk-in และรับจองทางโทรศัพท์)
- ทุกการจองเก็บ **snapshot** ของราคาและนโยบายยกเลิก ณ เวลาที่สร้างการจอง (BR-05)

### 5.1 Booker

**US-01 สมัครและเข้าสู่ระบบ**
ในฐานะผู้เล่น ฉันต้องการสมัครสมาชิกด้วยอีเมลหรือ LINE เพื่อจองคอร์ทได้
- [ ] สมัครด้วยอีเมล + รหัสผ่าน (อย่างน้อย 8 ตัวอักษร) และต้องยืนยันอีเมลก่อนจองได้
- [ ] LINE Login สร้างบัญชีให้อัตโนมัติ ถ้าไม่มีเบอร์โทร ต้องขอเบอร์โทรก่อนจองครั้งแรก
- [ ] ต้องยอมรับนโยบายความเป็นส่วนตัวตอนสมัคร และระบบบันทึกเวลากับเวอร์ชันของนโยบายที่ยอมรับ
- [ ] เลือกภาษา TH/EN ได้ และระบบจำค่าไว้ในบัญชี
- [ ] ล็อกอินผิด 5 ครั้งภายใน 15 นาที บัญชีถูกล็อก 15 นาที และส่งอีเมลแจ้งเจ้าของบัญชี

**US-02 ค้นหาสนามและดูตารางว่าง**
- [ ] ค้นหาสนามตามชื่อหรือเขต/จังหวัด และเลือกวันที่ได้ล่วงหน้าสูงสุด 30 วัน ⚠️ S-04
- [ ] ตารางแสดงคอร์ท × ชั่วโมง พร้อมสถานะ: ว่าง / ไม่ว่าง / ปิด และราคาต่อชั่วโมง โดยไม่เปิดเผยข้อมูลผู้จองคนอื่น
- [ ] ตารางรีเฟรชอัตโนมัติทุก 10 วินาทีขณะเปิดหน้าอยู่ และ server ตรวจความว่างซ้ำทุกครั้งที่กดจอง
- [ ] ผู้ที่ยังไม่ login ดูตารางได้ แต่ต้อง login ก่อนจอง
- [ ] ส่ง event `venue_page_viewed` ทุกครั้งที่เปิดหน้าสนาม
- [ ] เกณฑ์ performance: ดูหัวข้อ 8

**US-03 จองคอร์ท**
- [ ] เลือกได้หลายช่องเวลาในสนามเดียว และเห็นสรุปรายการพร้อมราคารวมก่อนยืนยัน
- [ ] ทุกช่องต้องเริ่มหลังเวลาปัจจุบันอย่างน้อย 30 นาที ⚠️ S-25
- [ ] ราคาคำนวณตามช่วงราคาของแต่ละช่อง (BR-05)
- [ ] ถ้าสองคนจองช่องเวลาเดียวกันพร้อมกัน ต้องสำเร็จเพียงคนเดียว อีกคนได้ข้อความว่า "ช่องเวลานี้เพิ่งถูกจอง" และทั้งการจองนั้นไม่ถูกสร้าง (BR-04)
- [ ] ผู้จองหนึ่งคนมีการจองในสถานะ `Held` ได้ครั้งละ 1 รายการ ⚠️ S-22
- [ ] เมื่อยืนยัน ระบบสร้างการจองสถานะ `Held` (BR-02)

**US-04 ชำระเงินด้วย PromptPay และอัปโหลดสลิป**
- [ ] แสดง QR PromptPay ของสนาม (ฝังยอดเงิน), ชื่อบัญชีผู้รับ และเวลาที่เหลือก่อนหมดเวลาล็อก
- [ ] อัปโหลดสลิปได้ (JPG/PNG/PDF ไม่เกิน 5 MB) แล้วสถานะเปลี่ยนเป็น `PendingVerification`
- [ ] ระหว่าง `PendingVerification` เปลี่ยนไฟล์สลิปได้ โดยระบบเก็บไฟล์เก่าไว้ใน audit log
- [ ] ถ้าอัปโหลดหลังหมดเวลาล็อก (ตัดสินด้วยเวลา server) ระบบปฏิเสธ พร้อมข้อความให้ติดต่อสนามถ้าโอนเงินไปแล้ว (6.1)
- [ ] ถ้า hash ของไฟล์ตรงกับสลิปที่เคยใช้ **ในสนามเดียวกัน** ระบบยังรับไฟล์ แต่ติดป้าย "สลิปซ้ำ" ในคิวตรวจของสนาม โดยไม่แจ้งผู้จอง (BR-07)

**US-05 ประวัติการจองและการยกเลิก**
- [ ] เห็นรายการจองทั้งหมดพร้อมสถานะ แยกเป็นรายการที่กำลังจะมาถึงกับที่ผ่านมาแล้ว และเห็นยอดต้องคืนกับยอดที่สนามคืนแล้ว
- [ ] ยกเลิกได้จากสถานะ `Held`, `PendingVerification`, `Confirmed` และต้องยกเลิกก่อนเวลาเริ่มเล่น (6.1)
- [ ] ก่อนกดยกเลิก ระบบแสดงยอดที่จะได้คืนตาม BR-06 (ถ้ายกเลิกจาก `PendingVerification` แสดงว่า "คืน 100% เมื่อสนามยืนยันว่าได้รับเงิน")
- [ ] เมื่อยกเลิก ช่องเวลากลับมาว่าง และถ้ายอดต้องคืน > 0 หรือต้องรอสนามยืนยันการรับเงิน สนามได้รับแจ้ง (US-17)

**US-06 แจ้งเตือนผู้จองทางอีเมล**
- [ ] ส่งอีเมลเมื่อเกิดเหตุการณ์: สร้างการจอง (รอจ่าย), สนามยืนยัน, สนามปฏิเสธ (พร้อมเหตุผล), หมดเวลาล็อก, ยกเลิก (ไม่ว่าผู้จองหรือสนามเป็นคนยกเลิก พร้อมเหตุผลและยอดต้องคืน), สนามบันทึกการคืนเงิน
- [ ] ส่งอีเมลเตือนก่อนเวลาเริ่มเล่น 2 ชั่วโมง เฉพาะการจอง `Confirmed` ⚠️ S-05
- [ ] อีเมลเป็นภาษาเดียวกับที่ผู้ใช้เลือก
- [ ] การจองช่องทาง `Staff` ไม่ส่งอีเมล (ลูกค้าไม่มีบัญชี)

**US-07 เอกสารสำหรับผู้จอง**
- [ ] เมื่อการจองเป็น `Confirmed` (ทั้งช่องทาง `Online` และ `Staff`) ระบบออกเอกสารค่าเริ่มต้นตามหัวข้อ 7.1 เป็น PDF · ผู้จองดาวน์โหลดได้จากประวัติ ส่วนการจองช่องทาง `Staff` ผู้มีสิทธิ์ `ManageBookings` ดาวน์โหลดให้ลูกค้า
- [ ] ตอนส่งมอบ story นี้ ระบบออกเอกสารย้อนหลังให้การจอง `Confirmed` ที่เกิดก่อนหน้า (บน UAT ก่อน pilot)
- [ ] ขอใบกำกับภาษีเต็มรูปได้ โดยกรอกชื่อ, ที่อยู่, เลขประจำตัวผู้เสียภาษี และสาขาของผู้ซื้อ ต้องขอภายในเดือนปฏิทินเดียวกับ **วันที่สนามยืนยันการชำระเงิน** ⚠️ S-06
- [ ] เมื่อออกใบกำกับภาษีเต็มรูป ระบบยกเลิกใบกำกับภาษีอย่างย่อฉบับเดิม และบันทึกว่าสองฉบับเชื่อมกัน (Q1)
- [ ] สนามที่ไม่ได้จด VAT ไม่แสดงปุ่มขอใบกำกับภาษี

### 5.2 สนาม

**US-10 สมัครเข้าร่วม platform**
- [ ] กรอกข้อมูลสนาม: ชื่อ, รหัสสนาม 3–6 ตัวอักษร (ใช้เป็นคำนำหน้าเลขที่เอกสาร), ที่อยู่, พิกัด, รูปภาพ, PromptPay ID + ชื่อบัญชี, สถานะ VAT, ชื่อผู้ประกอบการ, เลขประจำตัวผู้เสียภาษี, สาขา และที่อยู่สำหรับออกเอกสาร
- [ ] ต้องยอมรับข้อตกลงสำหรับสนาม ซึ่งรวมการมอบหมายให้ platform ออกเอกสารในนามของสนาม (Q8)
- [ ] สถานะของสนาม: `Pending` → `Approved` หรือ `Rejected` · `Approved` ↔ `Suspended` · สนามที่ `Rejected` แก้ไขข้อมูลแล้วส่งใหม่ได้ (กลับเป็น `Pending`)
- [ ] ผู้จองเห็นเฉพาะสนาม `Approved`
- [ ] ผู้สมัครกลายเป็น Owner ของสนามนั้น

**US-11 ตั้งค่าสนาม** (ต้องมีสิทธิ์ `ManageSettings` ยกเว้นการปิดคอร์ทที่ใช้ `CloseCourt`)
- [ ] เพิ่ม/แก้ไข/ปิดใช้งานคอร์ท (ปิดใช้งานได้เฉพาะคอร์ทที่ไม่มีการจอง active ในอนาคต) และเก็บประวัติวันที่เปิด/ปิดใช้งาน
- [ ] ตั้งเวลาเปิด-ปิดแยกตามวันในสัปดาห์ โดยระบุวันที่มีผล ระบบเก็บประวัติไว้ และไม่ให้บันทึกถ้าทำให้การจอง active อยู่นอกเวลาเปิด
- [ ] ตั้งช่วงราคาตามวันและช่วงเวลา ถ้าช่วงราคาซ้อนกันหรือมีชั่วโมงที่เปิดแต่ไม่มีราคา ระบบไม่ให้บันทึก
- [ ] ปิดคอร์ทชั่วคราวเป็นช่วงวันเวลา ถ้าทับการจอง active ระบบแสดงรายการที่กระทบ และ **ไม่ให้บันทึก** จนกว่าสนามจะยกเลิกการจองเหล่านั้นด้วยเหตุผล `VenueInitiated` (6.1)
- [ ] ตั้งนโยบายยกเลิกได้ 1–3 ขั้น แต่ละขั้นคือ "ยกเลิกก่อนเวลาเริ่มเล่น ≥ N ชั่วโมง คืน P%" (N เป็นจำนวนเต็ม ≥ 0, P เป็น 0–100 และขั้นที่ N มากกว่าต้องมี P ไม่น้อยกว่า) ถ้าไม่เข้าขั้นใดเลยคืน 0% · ค่าเริ่มต้น: ≥ 24 ชม. คืน 100% ⚠️ S-11
- [ ] การเปลี่ยนราคาและนโยบายมีผลเฉพาะการจองที่สร้างหลังจากนั้น

**US-12 ตรวจสลิป** (ต้องมีสิทธิ์ `VerifySlip`)
- [ ] คิวรายการ `PendingVerification` เรียงจากเก่าไปใหม่ แสดงรูปสลิป, ยอดที่ต้องจ่าย, ชื่อผู้จอง, เวลาอัปโหลด, ป้าย "สลิปซ้ำ" (ถ้ามี) และป้าย "ใกล้ถึงเวลาเล่น" สำหรับรายการที่เหลือไม่ถึง 1 ชม.
- [ ] กดยืนยัน → `Confirmed` (บันทึกว่าได้รับเงินแล้ว) หรือกดปฏิเสธ → `Rejected` ตอนปฏิเสธต้องระบุเหตุผล และต้องเลือกว่า "ได้รับเงินจริง" หรือ "ไม่ได้รับเงิน" ซึ่งกำหนดยอดต้องคืน (6.1)
- [ ] ตรวจได้แม้เลยเวลาเริ่มเล่นไปแล้ว (ผลลัพธ์ตาม 6.1)
- [ ] บันทึก audit log ว่าใครทำอะไรและเมื่อไร

**US-13 จองและจัดการการจองโดยพนักงาน** (ต้องมีสิทธิ์ `ManageBookings`)
- [ ] สร้างการจองช่องทาง `Staff` จากตารางได้ โดยกรอกชื่อลูกค้า (บังคับ), เบอร์โทร (ไม่บังคับ) และวิธีจ่าย (เงินสด / โอน) · จองช่องที่เริ่มไปแล้วแต่ยังไม่จบได้
- [ ] การจองนี้เริ่มที่สถานะ `Confirmed` และบันทึกว่าได้รับเงินแล้ว ลูกค้าไม่ต้องมีบัญชี (เอกสาร: US-07)
- [ ] ยกเลิกการจองได้ทุกช่องทาง:
  - จาก `Held`: ไม่ต้องระบุเหตุผล
  - จาก `PendingVerification`: ต้องเลือกว่าได้รับเงินหรือไม่
  - จาก `Confirmed` หรือ `Completed`: ต้องเลือกเหตุผลหนึ่งใน `CustomerRequest`, `VenueInitiated`, `PaymentNotReceived`
  - ระบบแสดงยอดต้องคืนตาม 6.1 ก่อนให้กดยืนยัน
- [ ] ยืนยันการรับเงิน (ได้รับ / ไม่ได้รับ) ของการจองที่ผู้จองยกเลิกจาก `PendingVerification`

- [ ] **อัตราการใช้คอร์ท (%)** = คอร์ท-ชั่วโมงที่ขายได้ซึ่งมีการจอง `Confirmed`/`Completed`/`NoShow` ÷ คอร์ท-ชั่วโมงที่ขายได้ทั้งหมด
  - คอร์ท-ชั่วโมงที่ขายได้ = คอร์ทเปิดใช้งาน ณ ชั่วโมงนั้น, อยู่ในเวลาเปิด-ปิดที่มีผล ณ วันนั้น (ประวัติจาก US-11) และไม่ได้ถูกปิด
  - คอร์ท-ชั่วโมงหนึ่งนับได้ไม่เกิน 1 ครั้ง (เช่น `NoShow` แล้วมี walk-in ต่อ นับครั้งเดียว) ค่าจึงไม่เกิน 100%

### 6.1 State machine ของการจอง (BR-03)

```
            upload slip               staff verify              ระบบ: เวลาจบ
  [Held] ─────────────────► [PendingVerification] ──────────► [Confirmed] ─────────────► [Completed]
    │  ▲ re-upload (วนที่เดิม) │   │                             │                          │  ▲
    │                        │   │ staff reject                 │ staff: NoShow            │  │ Owner แก้
    │ ระบบ: HoldExpiresAt     │   ▼                              ▼                          ▼  │
    ▼                        │ [Rejected]                    [NoShow] ◄─── staff: NoShow ───┘  │
 [Expired]                   │                                   └──────── Owner แก้ ─────────┘
                             └──── cancel ────► [Cancelled] ◄── cancel ── (Held, Confirmed, Completed*)
```
\* `Completed → Cancelled` ทำได้เฉพาะ Owner ภายในช่วงแก้ไข

**ช่วงแก้ไข** = ตั้งแต่เวลาจบ ถึงก่อนเวลาจบ + 24 ชั่วโมง (ไม่รวมจุดสิ้นสุด)

**กฎทั่วไปของ state machine**
- `Expired`, `Rejected`, `Cancelled` เป็นสถานะสุดท้าย ส่วน `Completed` และ `NoShow` เป็นสถานะสุดท้ายเมื่อพ้นช่วงแก้ไข
- ผู้จองที่ถูกปฏิเสธต้องสร้างการจองใหม่
- **ห้ามเปลี่ยนจาก `Confirmed` เป็น `Rejected`** ถ้ายืนยันผิด ให้ยกเลิกด้วยเหตุผลที่ตรงกับกรณีแทน
- ทุกการเปลี่ยนสถานะต้องตรวจสิทธิ์ตามคอลัมน์ "ใครทำ" บันทึก audit log (ใคร, เมื่อไร, เหตุผล) และส่ง event (หัวข้อ 8)

## 9. แนวทางทางเทคนิค

### 9.1 Architecture
```
Angular SPA (PWA) ──HTTPS──► Caddy ──/api──► ASP.NET Core Web API ──EF Core──► PostgreSQL
                                        │
                                        ├── S3-compatible storage นอกเครื่อง (สลิป, หลักฐานการคืนเงิน/ชำระ, PDF, backup)
                                        ├── Scheduled jobs (Expired, Completed, เตือนก่อนเล่น, สลิปค้างตรวจ, คอมมิชชันวันที่ 2)
                                        ├── Email service
                                        └── LINE Login (MVP) · LINE Messaging API/LIFF (เฟส 2)
```

### 9.2 ประเด็นทางเทคนิคสำคัญ
- **Multi-tenant:** ใช้ database เดียวร่วมกัน ตารางของสนามมี `VenueId` · บังคับด้วย EF Core global query filter + authorization policy ที่ตรวจทั้ง "สนามที่กำลังจัดการ" และสิทธิ์ (US-14)
- **กันจองซ้อน (BR-04):** PostgreSQL exclusion constraint บน `(court_id, tstzrange(start, end))` ของตาราง BookingSlot สำหรับแถวที่ `is_active = true`
  - ทุกการเปลี่ยนสถานะที่กระทบ active ต้องอัปเดต `is_active` ใน transaction เดียวกัน
  - ถ้า `NoShow → Completed` ชน constraint ให้ตอบ error ที่อ่านเข้าใจได้ (6.1)
- **Held ที่หมดเวลา:** ต้องไม่พึ่ง scheduled job อย่างเดียว เพราะ job อาจช้าหรือ container อาจ restart (R3)
  - ทุก query ที่ตรวจความว่าง และตอนสร้างการจองใหม่ ถือว่า `Held` ที่ `HoldExpiresAt < now` ไม่ active และปล่อยช่องนั้นใน transaction
  - job ยังคงทำหน้าที่เปลี่ยนสถานะเป็น `Expired` ภายหลัง
- **Confirmed ที่เลยเวลาจบ:** ทุก query และทุกการตรวจเงื่อนไขในหัวข้อ 6.1 ถือว่าเป็น `Completed` ทันที แม้ job ยังไม่รัน
- **Scheduled jobs:** ใช้ hosted service ใน container ของ API (เครื่องเปิดตลอด) · ทุก job ต้อง idempotent (รันซ้ำได้โดยไม่เกิดผลซ้ำ) · ถ้า container restart ต้องตามทำงานที่ค้างได้ · job คอมมิชชันต้องไม่นับการจองซ้ำข้ามใบแจ้งหนี้ · ทุก job ส่ง heartbeat ไปที่ uptime monitor (9.3)
- **QR PromptPay:** server สร้าง payload ตามมาตรฐาน EMVCo QR พร้อมยอดเงิน
- **เลขที่เอกสาร:** ใช้ตาราง counter ที่ล็อกแถวใน transaction เดียวกับการสร้างเอกสาร (ไม่ใช้ sequence ของ database เพราะ sequence ข้ามเลขได้)
- **PDF:** เลือก library ใน M1 โดยต้องตรวจ license ว่าใช้เชิงพาณิชย์ได้ฟรี · **ต้อง embed ฟอนต์ไทย** (เช่น Sarabun หรือ Noto Sans Thai) ไว้ในโปรเจกต์ เพราะ Linux ไม่มีฟอนต์ไทยติดมา
- **.NET บน Linux:**
  - ใช้ image `mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled-extra` ซึ่งมี ICU + tzdata ห้ามใช้ image ที่ไม่มี เพราะ `Asia/Bangkok` (BR-10) และ culture ไทยจะทำงานผิด
  - build image แบบ multi-arch `linux/amd64,linux/arm64` (UAT เป็น ARM)
  - ใช้ `.gitattributes` บังคับ LF สำหรับ shell script และไฟล์ config
  - ระวังชื่อไฟล์และ path แยกตัวพิมพ์เล็ก-ใหญ่ (CI รันบน Linux จึงจับได้)

### 9.3 Server (Linux) ⚠️ S-17
| Env | เครื่อง | หมายเหตุ |
|---|---|---|
| UAT | Oracle Cloud Always Free (ARM64) | ฟรี · ตรวจเงื่อนไขล่าสุดตอนสมัคร (capacity, การเรียกคืนเครื่องที่ใช้งานน้อย) · ต้องสร้างเครื่องใหม่ได้จาก compose + seed ภายใน 1 ชม. |
| PRD | VPS เสียเงิน 2 vCPU / 4 GB RAM / SSD 80 GB, region Singapore | เช่าภายใน M3 · เปิด snapshot/backup ของผู้ให้บริการ · งบ: Q6 |

**Software บนเครื่อง:** Ubuntu Server 24.04 LTS + Docker Engine + Docker Compose แต่ละ env เป็น compose project แยกกัน (database, secrets, domain แยก):
- `caddy`: reverse proxy + HTTPS อัตโนมัติ เสิร์ฟไฟล์ Angular และส่ง `/api` ไปที่ API
- `api`: ASP.NET Core (รวม scheduled jobs)
- `db`: PostgreSQL (volume บนเครื่อง ไม่เปิด port ออก internet)
- ไฟล์สลิป, หลักฐาน, PDF และ backup เก็บที่ S3-compatible storage นอกเครื่อง

**Hardening** (UAT ทำใน M1, PRD ทำใน M3)
- [ ] Login ด้วย SSH key เท่านั้น ปิด password login และ root login
- [ ] `ufw` เปิดเฉพาะ port 22, 80, 443
- [ ] `fail2ban` + `unattended-upgrades`
- [ ] Secrets อยู่ในไฟล์ `.env` บนเครื่อง (`chmod 600`) ไม่อยู่ใน git
- [ ] `pg_dump` ทุกวันแบบเข้ารหัสไปที่ storage นอกเครื่อง เก็บ 14 วัน และทดสอบกู้คืนเดือนละครั้ง
- [ ] Uptime monitor ภายนอก: ตรวจ health endpoint และรับ heartbeat จาก backup และ scheduled jobs
- [ ] แจ้งเตือนเมื่อพื้นที่ disk ถูกใช้เกิน 80%

### 9.4 Testing และ CI/CD
- Backend: xUnit + integration test กับ PostgreSQL จริงผ่าน Testcontainers **(ต้องติดตั้ง Docker)**
- Frontend: unit test ของ Angular + E2E ด้วย Playwright
- **Test ที่ต้องมีเสมอ:** จองพร้อมกันต้องไม่ซ้อน, ทุกแถวในตาราง 6.1 (ทั้งที่อนุญาตและที่ต้องถูกปฏิเสธ), ทุกนิยามในหัวข้อ 6.2, การคำนวณคอมมิชชันรวมกรณียกยอด, แยกข้อมูลระหว่างสนาม, เลขที่เอกสารไม่ข้ามเมื่อออกพร้อมกัน
- **GitHub Actions**
  - ทุก PR: build + test + security scan
  - merge เข้า `main`: deploy ไป UAT อัตโนมัติ ยกเว้นช่วงที่ประกาศเป็น "ช่วงสนามทดสอบ" ซึ่งต้องกด deploy เอง
  - deploy ไป PRD: เจ้าของโปรเจกต์กดอนุมัติใน GitHub หลัง UAT ผ่าน checklist ของ release
  - ขั้นตอน deploy (ทั้ง UAT และ PRD): build Docker image แบบ multi-arch → push ไป GitHub Container Registry → SSH เข้าเครื่อง → รัน EF Core migration bundle → `docker compose pull && docker compose up -d` → ตรวจ health endpoint
