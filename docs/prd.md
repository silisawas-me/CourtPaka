## 1. ภาพรวมและเป้าหมาย

### 1.1 ปัญหา ⚠️ S-01 (ต้องยืนยันกับสนาม pilot)
- **ผู้เล่น:** ต้องทัก LINE หรือโทรหาสนามทีละแห่งเพื่อถามว่าคอร์ทว่างไหม ไม่เห็นราคาและตารางล่วงหน้า และรอสนามตอบนาน
- **สนาม:** จัดตารางด้วยสมุด, LINE หรือ Excel ทำให้เกิดการจองซ้อน ต้องตรวจสลิปด้วยมือ และสรุปรายได้หรือทำเอกสารภาษีได้ยาก

### 1.2 เป้าหมาย
- **G1:** ผู้เล่นหาคอร์ทว่างและจองเสร็จได้เองโดยไม่ต้องทักสนาม
- **G2:** สนามลดงานจัดตาราง ตรวจสลิป และทำเอกสารภาษี
- **G3:** Platform มีรายได้จากค่าคอมมิชชัน และขยายไปสนามอื่นได้

### 1.3 ตัวชี้วัดความสำเร็จ (วัดช่วง pilot M4) ⚠️ S-02
| ตัวชี้วัด | เป้าหมาย | วัดจาก |
|---|---|---|
| สนามที่ใช้งานจริง | 5 สนาม | จำนวนสนาม `Approved` ที่มีการจองทุกสัปดาห์ |
| สัดส่วนชั่วโมงที่ขายได้ซึ่งบันทึกในระบบ (ออนไลน์ + walk-in) | ≥ 70% | เทียบกับยอดที่สนามแจ้ง |
| เวลาตั้งแต่เปิดหน้าสนามจนอัปโหลดสลิป (median) | ≤ 3 นาที | `venue_page_viewed` → `slip_uploaded` |
| เวลาตั้งแต่อัปโหลดสลิปจนสนามตรวจเสร็จ (median) | ≤ 15 นาที | `slip_uploaded` → `booking_confirmed` / `booking_rejected` |
| การจองซ้อน | 0 ครั้ง | |
| เอกสารภาษีที่ต้องยกเลิกเพราะระบบคำนวณหรือออกผิด | 0 ฉบับ | |

## 2. ผู้ใช้และบทบาท
| บทบาท | คือใคร | ทำอะไรในระบบ |
|---|---|---|
| **Booker** (ผู้จอง) | ผู้เล่นแบดมินตันทั่วไป | ค้นหาสนาม, จอง, จ่ายเงินและอัปโหลดสลิป, ยกเลิก, ดูประวัติ, ขอใบกำกับภาษีเต็มรูป |
| **Venue Owner** (เจ้าของสนาม) | ผู้สมัครสนามเข้า platform | มีทุกสิทธิ์ของสนามตัวเอง รวมถึงสิทธิ์ที่เป็นของ Owner เท่านั้น (ตาราง US-14) |
| **Venue Staff** (พนักงานสนาม) | ผู้ที่ Owner เชิญเข้าระบบ | ทำได้ตามสิทธิ์ที่ได้รับ (ตาราง US-14) |
| **Platform Admin** | ผู้ดูแล platform (เจ้าของโปรเจกต์) | อนุมัติหรือระงับสนามและผู้ใช้, ตั้งอัตราคอมมิชชัน, ตรวจการชำระค่าคอมมิชชัน, ดูภาพรวม, จัดการเรื่องร้องเรียน |

**กฎบัญชีผู้ใช้**
- ผู้ใช้หนึ่งบัญชีมีได้หลายบทบาท และเป็น Staff ได้หลายสนาม
- หนึ่งสนามมี Owner ได้ 1 บัญชี ส่วน Owner หนึ่งบัญชีมีได้หลายสนาม ⚠️ S-20
- ผู้ที่ทำงานกับหลายสนามต้องเลือก "สนามที่กำลังจัดการ" ก่อนทุกครั้ง ระบบจะแสดงข้อมูลเฉพาะสนามนั้นและไม่มีมุมมองรวมหลายสนาม ยกเว้น Platform Admin
- ข้อมูลของแต่ละสนามต้องแยกจากกันเด็ดขาด (หัวข้อ 8)

## 5. User Stories และ Acceptance Criteria (MVP)

### 5.0 โมเดลการจอง (ใช้กับทุก story)
- **การจอง (Booking)** 1 รายการ = ช่องเวลา (BookingSlot) 1 ช่องขึ้นไปในสนามเดียว มีสถานะเดียว, QR เดียว และสลิปเดียว
- ยกเลิกได้ทั้งการจองเท่านั้น **ไม่มีการยกเลิกบางช่อง** ⚠️ S-21
- "เวลาเริ่มเล่น" = เวลาเริ่มของช่องแรกสุด · "เวลาจบ" = เวลาจบของช่องสุดท้าย
- ช่องทางการจอง: `Online` (ผู้จองสร้างเอง) หรือ `Staff` (พนักงานสร้างให้ลูกค้า ทั้ง walk-in และรับจองทางโทรศัพท์)
- ทุกการจองเก็บ **snapshot** ของราคาและนโยบายยกเลิก ณ เวลาที่สร้างการจอง (BR-05)

### 5.1 Booker

**US-01 สมัครและเข้าสู่ระบบ**
ในฐานะผู้เล่น ฉันต้องการสมัครสมาชิกด้วยอีเมลหรือ LINE เพื่อจองคอร์ทได้
- [ ] สมัครด้วยอีเมล + รหัสผ่าน (อย่างน้อย 8 ตัวอักษร) และต้องยืนยันอีเมลก่อนจองได้
- [ ] LINE Login สร้างบัญชีให้อัตโนมัติ ถ้าไม่มีเบอร์โทร ต้องขอเบอร์โทรก่อนจองครั้งแรก
- [ ] ต้องยอมรับนโยบายความเป็นส่วนตัวตอนสมัคร และระบบบันทึกเวลากับเวอร์ชันของนโยบายที่ยอมรับ
- [ ] เลือกภาษา TH/EN ได้ และระบบจำค่าไว้ในบัญชี
- [ ] ล็อกอินผิด 5 ครั้งภายใน 15 นาที บัญชีถูกล็อก 15 นาที และส่งอีเมลแจ้งเจ้าของบัญชี

**US-02 ค้นหาสนามและดูตารางว่าง**
- [ ] ค้นหาสนามตามชื่อหรือเขต/จังหวัด และเลือกวันที่ได้ล่วงหน้าสูงสุด 30 วัน ⚠️ S-04
- [ ] ตารางแสดงคอร์ท × ชั่วโมง พร้อมสถานะ: ว่าง / ไม่ว่าง / ปิด และราคาต่อชั่วโมง โดยไม่เปิดเผยข้อมูลผู้จองคนอื่น
- [ ] ตารางรีเฟรชอัตโนมัติทุก 10 วินาทีขณะเปิดหน้าอยู่ และ server ตรวจความว่างซ้ำทุกครั้งที่กดจอง
- [ ] ผู้ที่ยังไม่ login ดูตารางได้ แต่ต้อง login ก่อนจอง
- [ ] ส่ง event `venue_page_viewed` ทุกครั้งที่เปิดหน้าสนาม
- [ ] เกณฑ์ performance: ดูหัวข้อ 8

**US-03 จองคอร์ท**
- [ ] เลือกได้หลายช่องเวลาในสนามเดียว และเห็นสรุปรายการพร้อมราคารวมก่อนยืนยัน
- [ ] ทุกช่องต้องเริ่มหลังเวลาปัจจุบันอย่างน้อย 30 นาที ⚠️ S-25
- [ ] ราคาคำนวณตามช่วงราคาของแต่ละช่อง (BR-05)
- [ ] ถ้าสองคนจองช่องเวลาเดียวกันพร้อมกัน ต้องสำเร็จเพียงคนเดียว อีกคนได้ข้อความว่า "ช่องเวลานี้เพิ่งถูกจอง" และทั้งการจองนั้นไม่ถูกสร้าง (BR-04)
- [ ] ผู้จองหนึ่งคนมีการจองในสถานะ `Held` ได้ครั้งละ 1 รายการ ⚠️ S-22
- [ ] เมื่อยืนยัน ระบบสร้างการจองสถานะ `Held` (BR-02)

**US-04 ชำระเงินด้วย PromptPay และอัปโหลดสลิป**
- [ ] แสดง QR PromptPay ของสนาม (ฝังยอดเงิน), ชื่อบัญชีผู้รับ และเวลาที่เหลือก่อนหมดเวลาล็อก
- [ ] อัปโหลดสลิปได้ (JPG/PNG/PDF ไม่เกิน 5 MB) แล้วสถานะเปลี่ยนเป็น `PendingVerification`
- [ ] ระหว่าง `PendingVerification` เปลี่ยนไฟล์สลิปได้ โดยระบบเก็บไฟล์เก่าไว้ใน audit log
- [ ] ถ้าอัปโหลดหลังหมดเวลาล็อก (ตัดสินด้วยเวลา server) ระบบปฏิเสธ พร้อมข้อความให้ติดต่อสนามถ้าโอนเงินไปแล้ว (6.1)
- [ ] ถ้า hash ของไฟล์ตรงกับสลิปที่เคยใช้ **ในสนามเดียวกัน** ระบบยังรับไฟล์ แต่ติดป้าย "สลิปซ้ำ" ในคิวตรวจของสนาม โดยไม่แจ้งผู้จอง (BR-07)

**US-05 ประวัติการจองและการยกเลิก**
- [ ] เห็นรายการจองทั้งหมดพร้อมสถานะ แยกเป็นรายการที่กำลังจะมาถึงกับที่ผ่านมาแล้ว และเห็นยอดต้องคืนกับยอดที่สนามคืนแล้ว
- [ ] ยกเลิกได้จากสถานะ `Held`, `PendingVerification`, `Confirmed` และต้องยกเลิกก่อนเวลาเริ่มเล่น (6.1)
- [ ] ก่อนกดยกเลิก ระบบแสดงยอดที่จะได้คืนตาม BR-06 (ถ้ายกเลิกจาก `PendingVerification` แสดงว่า "คืน 100% เมื่อสนามยืนยันว่าได้รับเงิน")
- [ ] เมื่อยกเลิก ช่องเวลากลับมาว่าง และถ้ายอดต้องคืน > 0 หรือต้องรอสนามยืนยันการรับเงิน สนามได้รับแจ้ง (US-17)

**US-06 แจ้งเตือนผู้จองทางอีเมล**
- [ ] ส่งอีเมลเมื่อเกิดเหตุการณ์: สร้างการจอง (รอจ่าย), สนามยืนยัน, สนามปฏิเสธ (พร้อมเหตุผล), หมดเวลาล็อก, ยกเลิก (ไม่ว่าผู้จองหรือสนามเป็นคนยกเลิก พร้อมเหตุผลและยอดต้องคืน), สนามบันทึกการคืนเงิน
- [ ] ส่งอีเมลเตือนก่อนเวลาเริ่มเล่น **24 ชั่วโมง** และ **2 ชั่วโมง** เฉพาะการจอง `Confirmed` ⚠️ S-05
  - สองฉบับนี้ทำคนละหน้าที่: 24 ชั่วโมงเผื่อเวลาให้ยกเลิกแล้วสนามยังหาคนแทนทัน (คิวรอ US-27) ส่วน 2 ชั่วโมงคือการเตือนให้มา
  - การจองที่สร้างเมื่อเหลือเวลาน้อยกว่า 24 ชั่วโมงไม่ต้องส่งฉบับแรก (ไม่ใช่ส่งย้อนหลัง)
- [ ] อีเมลเป็นภาษาเดียวกับที่ผู้ใช้เลือก
- [ ] การจองช่องทาง `Staff` ไม่ส่งอีเมล (ลูกค้าไม่มีบัญชี)

**US-07 เอกสารสำหรับผู้จอง**
- [ ] เมื่อการจองเป็น `Confirmed` (ทั้งช่องทาง `Online` และ `Staff`) ระบบออกเอกสารค่าเริ่มต้นตามหัวข้อ 7.1 เป็น PDF · ผู้จองดาวน์โหลดได้จากประวัติ ส่วนการจองช่องทาง `Staff` ผู้มีสิทธิ์ `ManageBookings` ดาวน์โหลดให้ลูกค้า
- [ ] ตอนส่งมอบ story นี้ ระบบออกเอกสารย้อนหลังให้การจอง `Confirmed` ที่เกิดก่อนหน้า (บน UAT ก่อน pilot)
- [ ] ขอใบกำกับภาษีเต็มรูปได้ โดยกรอกชื่อ, ที่อยู่, เลขประจำตัวผู้เสียภาษี และสาขาของผู้ซื้อ ต้องขอภายในเดือนปฏิทินเดียวกับ **วันที่สนามยืนยันการชำระเงิน** ⚠️ S-06
- [ ] เมื่อออกใบกำกับภาษีเต็มรูป ระบบยกเลิกใบกำกับภาษีอย่างย่อฉบับเดิม และบันทึกว่าสองฉบับเชื่อมกัน (Q1)
- [ ] สนามที่ไม่ได้จด VAT ไม่แสดงปุ่มขอใบกำกับภาษี

### 5.2 สนาม

**US-10 สมัครเข้าร่วม platform**
- [ ] กรอกข้อมูลสนาม: ชื่อ, รหัสสนาม 3–6 ตัวอักษร (ใช้เป็นคำนำหน้าเลขที่เอกสาร), ที่อยู่, พิกัด, รูปภาพ, PromptPay ID + ชื่อบัญชี, สถานะ VAT, ชื่อผู้ประกอบการ, เลขประจำตัวผู้เสียภาษี, สาขา และที่อยู่สำหรับออกเอกสาร
- [ ] ต้องยอมรับข้อตกลงสำหรับสนาม ซึ่งรวมการมอบหมายให้ platform ออกเอกสารในนามของสนาม (Q8)
- [ ] สถานะของสนาม: `Pending` → `Approved` หรือ `Rejected` · `Approved` ↔ `Suspended` · สนามที่ `Rejected` แก้ไขข้อมูลแล้วส่งใหม่ได้ (กลับเป็น `Pending`)
- [ ] ผู้จองเห็นเฉพาะสนาม `Approved`
- [ ] ผู้สมัครกลายเป็น Owner ของสนามนั้น

**US-11 ตั้งค่าสนาม** (ต้องมีสิทธิ์ `ManageSettings` ยกเว้นการปิดคอร์ทที่ใช้ `CloseCourt`)
- [ ] เพิ่ม/แก้ไข/ปิดใช้งานคอร์ท (ปิดใช้งานได้เฉพาะคอร์ทที่ไม่มีการจอง active ในอนาคต) และเก็บประวัติวันที่เปิด/ปิดใช้งาน
- [ ] ตั้งเวลาเปิด-ปิดแยกตามวันในสัปดาห์ โดยระบุวันที่มีผล ระบบเก็บประวัติไว้ และไม่ให้บันทึกถ้าทำให้การจอง active อยู่นอกเวลาเปิด
- [ ] ตั้งช่วงราคาตามวันและช่วงเวลา ถ้าช่วงราคาซ้อนกันหรือมีชั่วโมงที่เปิดแต่ไม่มีราคา ระบบไม่ให้บันทึก
- [ ] ปิดคอร์ทชั่วคราวเป็นช่วงวันเวลา ถ้าทับการจอง active ระบบแสดงรายการที่กระทบ และ **ไม่ให้บันทึก** จนกว่าสนามจะยกเลิกการจองเหล่านั้นด้วยเหตุผล `VenueInitiated` (6.1)
- [ ] ตั้งนโยบายยกเลิกได้ 1–3 ขั้น แต่ละขั้นคือ "ยกเลิกก่อนเวลาเริ่มเล่น ≥ N ชั่วโมง คืน P%" (N เป็นจำนวนเต็ม ≥ 0, P เป็น 0–100 และขั้นที่ N มากกว่าต้องมี P ไม่น้อยกว่า) ถ้าไม่เข้าขั้นใดเลยคืน 0% · ค่าเริ่มต้น: ≥ 24 ชม. คืน 100% ⚠️ S-11
- [ ] การเปลี่ยนราคาและนโยบายมีผลเฉพาะการจองที่สร้างหลังจากนั้น

**US-12 ตรวจสลิป** (ต้องมีสิทธิ์ `VerifySlip`)
- [ ] คิวรายการ `PendingVerification` เรียงจากเก่าไปใหม่ แสดงรูปสลิป, ยอดที่ต้องจ่าย, ชื่อผู้จอง, เวลาอัปโหลด, ป้าย "สลิปซ้ำ" (ถ้ามี) และป้าย "ใกล้ถึงเวลาเล่น" สำหรับรายการที่เหลือไม่ถึง 1 ชม.
- [ ] กดยืนยัน → `Confirmed` (บันทึกว่าได้รับเงินแล้ว) หรือกดปฏิเสธ → `Rejected` ตอนปฏิเสธต้องระบุเหตุผล และต้องเลือกว่า "ได้รับเงินจริง" หรือ "ไม่ได้รับเงิน" ซึ่งกำหนดยอดต้องคืน (6.1)
- [ ] ตรวจได้แม้เลยเวลาเริ่มเล่นไปแล้ว (ผลลัพธ์ตาม 6.1)
- [ ] บันทึก audit log ว่าใครทำอะไรและเมื่อไร

**US-13 จองและจัดการการจองโดยพนักงาน** (ต้องมีสิทธิ์ `ManageBookings`)
- [ ] สร้างการจองช่องทาง `Staff` จากตารางได้ โดยกรอกชื่อลูกค้า (บังคับ), เบอร์โทร (ไม่บังคับ) และวิธีจ่าย (เงินสด / โอน) · จองช่องที่เริ่มไปแล้วแต่ยังไม่จบได้
- [ ] การจองนี้เริ่มที่สถานะ `Confirmed` และบันทึกว่าได้รับเงินแล้ว ลูกค้าไม่ต้องมีบัญชี (เอกสาร: US-07)
- [ ] ยกเลิกการจองได้ทุกช่องทาง:
  - จาก `Held`: ไม่ต้องระบุเหตุผล
  - จาก `PendingVerification`: ต้องเลือกว่าได้รับเงินหรือไม่
  - จาก `Confirmed` หรือ `Completed`: ต้องเลือกเหตุผลหนึ่งใน `CustomerRequest`, `VenueInitiated`, `PaymentNotReceived`
  - ระบบแสดงยอดต้องคืนตาม 6.1 ก่อนให้กดยืนยัน
- [ ] ยืนยันการรับเงิน (ได้รับ / ไม่ได้รับ) ของการจองที่ผู้จองยกเลิกจาก `PendingVerification`
- [ ] กด `NoShow` ได้ตาม 6.1
- [ ] **ล็อกคอร์ทไว้รอเงินโอนได้** โดยสร้างการจองช่องทาง `Staff` ที่สถานะ `Held` แทนที่จะเป็น `Confirmed` — ใช้เวลาล็อกเดียวกับ BR-02 (15 นาที) ไม่มีเวลาที่สอง · เมื่อเงินเข้าแล้วกดยืนยันเป็น `Confirmed` · ปล่อยเองเมื่อหมดเวลาเหมือนทุก `Held`

**US-15 Dashboard ของสนาม** (ต้องมีสิทธิ์ `ViewReports`) ใช้นิยามในหัวข้อ 6.2 และนับเข้าวันตาม **วันที่ใช้บริการ**
- [ ] **รายได้** รายวันและรายเดือน = ผลรวม **ยอดที่สนามเก็บไว้** ของการจองสถานะ `Completed`, `NoShow`, `Cancelled` แยกตามช่องทาง `Online` / `Staff`
- [ ] **ยอดจองล่วงหน้า** (ไม่ขึ้นกับตัวกรองวันที่) = ผลรวมยอดการจองสถานะ `Confirmed` ที่เวลาเริ่มเล่นยังไม่ถึง ณ ตอนเปิดดู
- [ ] **อัตราการใช้คอร์ท (%)** = คอร์ท-ชั่วโมงที่ขายได้ซึ่งมีการจอง `Confirmed`/`Completed`/`NoShow` ÷ คอร์ท-ชั่วโมงที่ขายได้ทั้งหมด
  - คอร์ท-ชั่วโมงที่ขายได้ = คอร์ทเปิดใช้งาน ณ ชั่วโมงนั้น, อยู่ในเวลาเปิด-ปิดที่มีผล ณ วันนั้น (ประวัติจาก US-11) และไม่ได้ถูกปิด
  - คอร์ท-ชั่วโมงหนึ่งนับได้ไม่เกิน 1 ครั้ง (เช่น `NoShow` แล้วมี walk-in ต่อ นับครั้งเดียว) ค่าจึงไม่เกิน 100%
- [ ] รายการที่ต้องจัดการ: `PendingVerification` ทั้งหมด, การจองที่ **รอยืนยันการรับเงิน** และการจองที่ **ค้างคืนเงิน**
- [ ] กรองตามช่วงวันที่ได้

**US-16 เอกสารและรายงานภาษีของสนาม** (ดูและ export: `ViewReports` · ยกเลิกเอกสาร: Owner เท่านั้น)
- [ ] ออกเลขที่เอกสารตามหัวข้อ 7.4 และมี test ยืนยันว่าเลขไม่ซ้ำและไม่ข้ามแม้ออกพร้อมกันหลายฉบับ
- [ ] ยกเลิกเอกสารได้โดยต้องระบุเหตุผล เอกสารที่ยกเลิกยังคงอยู่และแสดงคำว่า "ยกเลิก"
- [ ] Export รายงานภาษีขายรายเดือน (เฉพาะสนามที่จด VAT) และสรุปรายได้รายเดือน/รายปีเป็น Excel ตามคอลัมน์ในหัวข้อ 7.3

**US-17 แจ้งเตือนฝั่งสนาม**
- [ ] แจ้งในระบบ (ตัวเลขบนเมนู) + อีเมลถึงผู้มีสิทธิ์ที่เกี่ยวข้อง เมื่อ:
  - มีสลิปใหม่รอตรวจ หรือสลิปซ้ำ (ถึงผู้มี `VerifySlip`)
  - มีการจองที่ยอดต้องคืน > 0 หรือรอยืนยันการรับเงิน (ถึงผู้มี `ManageBookings`)
  - ใบแจ้งหนี้คอมมิชชันใหม่หรือเลยกำหนดชำระ (ถึง Owner, ส่งมอบพร้อม US-21 ใน M3)
- [ ] ถ้ามีรายการ `PendingVerification` ค้างอยู่เมื่อเหลือเวลาก่อนเล่น 30 นาที ส่งอีเมลเตือนถึง Owner ⚠️ S-23
- [ ] ผู้ใช้ปิดอีเมลแจ้งเตือนสลิปใหม่ได้ แต่ปิดการเตือนอื่นในเรื่องนี้ไม่ได้

**US-18 บันทึกการคืนเงิน** (ต้องมีสิทธิ์ `ManageBookings`)
- [ ] บันทึก Refund Record ได้เฉพาะการจองที่ **ค้างคืนเงิน** โดยกรอก ยอด (> 0 และไม่เกินยอดค้างคืน), วันที่คืน, วิธีคืน (โอน / เงินสด), หมายเหตุ และแนบหลักฐานได้ (ไม่บังคับ)
- [ ] บันทึกได้หลายครั้งจนครบยอด และแก้ไข Refund Record ไม่ได้
- [ ] Owner ยกเลิก Refund Record ได้โดยต้องระบุเหตุผล แล้วยอดค้างคืนจะกลับมา
- [ ] **วงเงินต่อรายการตามสมาชิก:** Owner ตั้งวงเงินคืนเงินของสมาชิกแต่ละคนได้ (ค่าเริ่มต้น 0 = บันทึกไม่ได้) · เกินวงเงินระบบปฏิเสธพร้อมบอกวงเงินที่มี ให้ส่งต่อให้คนที่มีวงเงินพอ — ไม่มีการอนุมัติข้ามด้วยรหัส เพราะรหัสที่ยืมกันได้ไม่ใช่การอนุมัติ · Owner ไม่มีวงเงิน
- [ ] การเปลี่ยนวงเงินบันทึกเป็นประวัติสิทธิ์เหมือนการเปลี่ยนสิทธิ์อื่น (PRD 8)
- [ ] ผู้จองได้รับอีเมลทุกครั้งที่บันทึก (US-06)

### 5.3 Platform Admin

**US-20 จัดการสนาม**
- [ ] อนุมัติหรือปฏิเสธสนามที่ `Pending` (ปฏิเสธต้องระบุเหตุผล และส่งอีเมลแจ้ง)
- [ ] ระงับหรือยกเลิกการระงับสนามได้ สนามที่ `Suspended`:

  - การจอง `Held` หมดเวลาตามปกติ หรือสนามยกเลิกได้ ส่วน `PendingVerification` สนามยังตรวจได้
  - การจอง `Confirmed` ในอนาคตยังคงอยู่ สนามต้องให้บริการหรือยกเลิกด้วยเหตุผล `VenueInitiated`
  - Owner และ Staff ยัง login เพื่อจัดการการจองที่มีอยู่และชำระค่าคอมมิชชันได้

**US-21 ค่าคอมมิชชัน**
- [ ] Admin ตั้งอัตราคอมมิชชันแยกรายสนามได้ โดยกำหนด **วันที่มีผล** และระบบใช้อัตราตามวันที่ใช้บริการของแต่ละการจอง พร้อมเก็บประวัติการเปลี่ยนอัตรา
- [ ] **วันที่ 2 เวลา 02:00** ระบบคำนวณตาม BR-08 และออกใบแจ้งหนี้ PDF ให้แต่ละสนาม พร้อมรายการการจองที่ใช้คำนวณ (รวมรายการยกยอดจากเดือนก่อน) ถ้ายอดเป็น 0 ไม่ต้องออก
- [ ] สถานะใบแจ้งหนี้: `Issued` → `PaymentSubmitted` → `Paid` · สถานะ `Overdue` = ยังไม่ `Paid` และวันนี้เลยวันครบกำหนดแล้ว (แสดงควบคู่กับสถานะอื่น)
- [ ] ใบแจ้งหนี้แสดงบัญชีรับเงินของ platform · Owner โอนเงินแล้วอัปโหลดหลักฐาน → `PaymentSubmitted` · Admin ตรวจแล้วกด `Paid` → ระบบออกเอกสารตามหัวข้อ 7.2 หรือกดปฏิเสธพร้อมเหตุผล → กลับเป็น `Issued`
- [ ] ใบแจ้งหนี้ที่ `Overdue` แสดงในหน้ารายการของ Admin และหน้าหลักของ Owner

**US-22 Dashboard ของ Platform, จัดการผู้ใช้ และเรื่องร้องเรียน**
- [ ] แสดงตามช่วงวันที่ที่เลือก: จำนวนการจองสถานะ `Confirmed`/`Completed`/`NoShow` ตามวันที่ใช้บริการ, GMV, สัดส่วน `Online` : `Staff` แยกรายสนาม · และแสดงจำนวนสนามแยกตามสถานะ (US-10) ณ ปัจจุบัน
- [ ] **GMV** = ผลรวมยอดที่สนามเก็บไว้ของการจองช่องทาง `Online` สถานะ `Completed`, `NoShow`, `Cancelled` ตามวันที่ใช้บริการ (รวมรายการที่ยังไม่ปิดยอด จึงอาจต่างจากยอดในใบแจ้งหนี้)
- [ ] **คอมมิชชันที่เก็บได้** = ผลรวมใบแจ้งหนี้ `Paid` · **คอมมิชชันที่ค้าง** = ผลรวมใบแจ้งหนี้ `Issued` + `PaymentSubmitted` (นับตามเดือนที่ออกใบแจ้งหนี้)
- [ ] ค้นหาผู้ใช้และระงับบัญชีได้ ผู้ใช้ที่ถูกระงับ login ไม่ได้ แต่การจอง `Confirmed` ในอนาคตยังคงอยู่
- [ ] เปิดเรื่องร้องเรียนได้ โดยอ้างอิงการจอง พร้อมรายละเอียดและช่องทางที่แจ้งเข้ามา · สถานะ `Open` / `Resolved` (ต้องบันทึกผลการแก้ไข)
- [ ] ดูสลิปของการจองได้เฉพาะตอนเรื่องร้องเรียนที่อ้างอิงยังเป็น `Open` และบันทึกทุกครั้งที่ดูไว้ใน audit log

**US-23 รองรับสองภาษา**
- [ ] ข้อความใน UI และอีเมลทั้งหมดดึงจากไฟล์แปลภาษา th/en
- [ ] มี test ใน CI ที่ fail เมื่อ key ของ th กับ en ไม่ครบคู่กัน
- [ ] API ส่ง error เป็นรหัส (error code) แล้ว frontend แปลเป็นข้อความตามภาษาที่เลือก
- [ ] เอกสารภาษีออกเป็นภาษาไทย ⚠️ S-07

### 5.4 หน้าเคาน์เตอร์ (จาก prototype CourtFlow v0.9)

Story ชุดนี้มาจาก prototype ที่ใช้คุยกับสนาม (`CourtFlow_SalesReady_Spec.md`) ซึ่งชี้ให้เห็นงานที่สนามทำทุกวันแต่ระบบยังไม่รองรับ: คนไม่มาตามจอง, เงินที่รับหน้าเคาน์เตอร์, และการปิดยอดตอนกลางคืน · ทั้งหมดอยู่ **นอก MVP** (M1–M3) และจะจัดเข้า milestone หลังจบ pilot เว้นแต่สนาม pilot บอกว่าขาดไม่ได้

**US-24 สถานะการมาและเช็กอิน** (ต้องมีสิทธิ์ `ManageBookings`)
ในฐานะพนักงานหน้าเคาน์เตอร์ ฉันต้องการรู้ว่าใครยืนยันว่าจะมาแล้วบ้าง เพื่อจะได้ตามคนที่ยังเงียบก่อนถึงเวลา
- [ ] การจองมี **สถานะการมา** แยกจากสถานะการจอง: `Unconfirmed` → `Reminded` → `Confirmed` → `Arrived` และเปลี่ยนได้ทางเดียว (ยกเลิกการจองทำให้จบ)
- [ ] สนามกด "ยืนยันว่าจะมา" แทนผู้จองได้ (เช่นโทรไปถาม) และกด "เช็กอิน" ได้ตั้งแต่ก่อนเวลาเริ่ม 30 นาที
- [ ] เมื่อถึงเวลาเริ่มเล่นแล้วยังไม่เช็กอิน ระบบนับ **ช่วงผ่อนผัน** (ค่าเริ่มต้น 15 นาที ตั้งได้รายสนาม) และแสดงเวลาที่เหลือ
- [ ] กด No-show ได้เมื่อพ้นช่วงผ่อนผันเท่านั้น (เดิมคือ 15 นาทีหลังเริ่มเล่น — กฎเดียวกัน แต่ตอนนี้ตั้งค่าได้)
- [ ] ทุกการเปลี่ยนสถานะการมาถูกบันทึกเป็น audit เหมือนการเปลี่ยนสถานะการจอง (PRD 8)
- [ ] เช็กอินไม่ได้ถ้าการจองยังไม่ `Confirmed` และระบบบอกยอดค้างชำระตอนเช็กอิน

**US-25 คอนโซลวันนี้ของสนาม** (ต้องมีสิทธิ์ `ManageBookings`)
ในฐานะพนักงาน ฉันต้องการเห็นทั้งวันในหน้าจอเดียว เพื่อไม่ต้องเปิดหลายหน้าเวลามีคนยืนรออยู่ตรงหน้า
- [ ] ตารางคอร์ท × ชั่วโมงของ **วันนี้** โดยการจองที่ยาวหลายชั่วโมงเป็นบล็อกเดียว พร้อมชื่อผู้จอง/ลูกค้า และเส้นบอกเวลาปัจจุบัน
- [ ] สีบอกสถานะ: กำลังเล่น / ยืนยันแล้ว / รอชำระหรือยังไม่ยืนยันว่าจะมา / ปิดปรับปรุง
- [ ] ตัวเลขของวันนี้: จำนวนการจอง, อัตราการใช้คอร์ท, ยอดที่รับแล้ว, ยอดค้างชำระ — นิยามเดียวกับ US-15 แต่ขอบเขตแค่วันนี้
- [ ] กดบล็อกเปิดรายละเอียดการจองพร้อมปุ่มที่ทำได้ตามสถานะ · กดช่องว่างเปิดฟอร์มขายหน้าเคาน์เตอร์ที่คอร์ท/เวลานั้น (US-13)
- [ ] ใช้งานบนมือถือหน้าเคาน์เตอร์ได้โดยไม่ต้องซูม

**US-26 รับเงินหลายช่องทางและปิดยอดประจำวัน** (ต้องมีสิทธิ์ `ManageBookings` · ปิดยอด: Owner หรือสิทธิ์ `ViewReports`)
- [ ] บันทึกการรับเงินได้หลายครั้งต่อการจอง (มัดจำแล้วจ่ายเพิ่ม) โดยแต่ละครั้งระบุยอด ช่องทาง (เงินสด / PromptPay / บัตร) และผู้รับเงิน
- [ ] รับเงินเกินยอดค้างไม่ได้ และยอดค้างของการจองคำนวณจากผลรวมที่รับ ลบด้วยที่คืน
- [ ] ปิดยอดประจำวัน: ยอดขาย, แยกตามช่องทาง, เงินสดตั้งต้น, เงินสดที่ควรมี, เงินสดจริงที่นับได้, ผลต่าง และเหตุผลเมื่อผลต่างไม่เป็นศูนย์
- [ ] ปิดยอดแล้วแก้ไม่ได้ (append-only เหมือน audit อื่น) และรายการรับเงินของวันนั้นยังเพิ่มได้ แต่จะปรากฏเป็นรายการของวันถัดไป
- [ ] ระบบช่วยชี้ว่าผลต่างน่าจะมาจากรายการไหน (รายการเงินสดที่ยอดเท่าผลต่าง, รายการที่ถูกแก้ยอด, ยอดค้างที่อาจรับเงินแล้วยังไม่บันทึก)

**US-27 คิวรอและการกู้รายได้** (ต้องมีสิทธิ์ `ManageBookings`)
- [ ] ผู้จองที่หาช่องว่างไม่ได้เข้าคิวรอได้ โดยระบุวัน ช่วงเวลา และจำนวนชั่วโมง
- [ ] เมื่อช่องเวลาว่างลง (ยกเลิก / No-show / ปล่อยจากการหมดเวลา) ระบบเสนอให้คิวแรกที่ตรงเงื่อนไข พร้อมกำหนดเวลาหมดอายุของข้อเสนอ
- [ ] ผู้จองตอบรับแล้วได้การจองปกติ (จ่ายตามกฎเดิม) · ปฏิเสธหรือหมดเวลาแล้วเสนอคิวถัดไปอัตโนมัติ
- [ ] สนามเห็นว่าช่องที่หลุดไปกี่ช่อง เติมกลับได้กี่ช่อง และคิดเป็นเงินเท่าไร

**US-28 กฎมัดจำตามประวัติการไม่มา**
- [ ] นับ No-show ของผู้จองย้อนหลัง 60 วัน แล้วจัดระดับ: 0–1 ไม่บังคับมัดจำ · 2 บังคับมัดจำครึ่งหนึ่ง · 3 ขึ้นไป ช่วงพีคต้องจ่ายเต็ม
- [ ] เงื่อนไขนี้บังคับตอนสร้างการจอง และบอกผู้จองว่าทำไมจึงต้องจ่าย
- [ ] ระดับเปลี่ยนทันทีที่บันทึก No-show และบันทึกไว้ใน audit
- [ ] สนามปรับเกณฑ์ได้ และปิดกฎนี้ได้ทั้งข้อ

**US-29 ต่อเวลาและย้ายคอร์ท** (ต้องมีสิทธิ์ `ManageBookings`)
ในฐานะพนักงาน ฉันต้องการต่อเวลาให้ก๊วนที่ยังเล่นอยู่ และย้ายคอร์ทให้คนที่เจอปัญหาหน้างาน โดยไม่ต้องยกเลิกแล้วจองใหม่
- [ ] **ต่อเวลา:** เพิ่มชั่วโมงถัดไปให้การจองที่กำลังเล่นอยู่หรือยังไม่จบ ถ้าคอร์ทเดิมว่างในชั่วโมงนั้น · ถ้าไม่ว่าง ระบบบอกว่าชั่วโมงนั้นมีคนแล้วและเสนอคอร์ทอื่นที่ว่าง (จะรับหรือไม่ก็ได้)
- [ ] **ชั่วโมงที่ต่อใช้ราคา ณ เวลาที่ต่อ ไม่ใช่ราคา snapshot ของการจองเดิม** — มันคือการซื้อเพิ่ม ไม่ใช่ส่วนหนึ่งของสิ่งที่ตกลงกันตอนจอง (BR-05 ยังคุมชั่วโมงเดิมไว้เหมือนเดิม)
- [ ] ยอดที่เพิ่มขึ้นกลายเป็นยอดค้างของการจองเดิม เก็บเงินตาม US-26 (ไม่สร้างการจองใบใหม่)
- [ ] **ย้ายคอร์ท:** ย้ายชั่วโมงที่ยังไม่จบไปคอร์ทอื่นที่ว่างในเวลาเดียวกัน · ราคาไม่เปลี่ยนแม้คอร์ทใหม่ราคาต่างกัน เพราะเป็นการย้ายที่สนามเป็นคนจัดให้ ไม่ใช่การซื้อใหม่ · ชั่วโมงที่เล่นจบไปแล้วย้ายไม่ได้
- [ ] ทั้งสองอย่าง **ไม่เปลี่ยนสถานะการจอง** และยังถูกกันจองซ้อนที่ระดับ database เหมือนทุกการเขียน (BR-04)
- [ ] ทุกครั้งที่ชั่วโมงของการจองเปลี่ยน บันทึกไว้ว่าใคร เมื่อไร จากอะไรเป็นอะไร (PRD 8) และผู้จองช่องทาง `Online` ได้รับอีเมล (US-06)

### 5.5 เฟส 2 — จองประจำและแพ็กเกจ (F8, F9)

หัวข้อ 4 กำหนดให้ AC ของเฟส 2 เขียนเสร็จภายใน M4 · สองข้อนี้มาจาก prototype CourtFlow v0.9 หัวข้อ 5.7
ซึ่งเป็นสองเรื่องที่สนามถามถึงบ่อยที่สุดตอนเอา prototype ไปคุย: ก๊วนที่มาทุกสัปดาห์ กับการขายชั่วโมงล่วงหน้า

**US-30 จองประจำทุกสัปดาห์** (ต้องมีสิทธิ์ `ManageBookings`)
ในฐานะสนาม ฉันต้องการตั้งก๊วนที่มาเวลาเดิมทุกสัปดาห์ไว้ครั้งเดียว เพื่อไม่ต้องจดและจองใหม่ทุกอาทิตย์
- [ ] สร้าง **ชุดการจองประจำ** จากคอร์ท + วันในสัปดาห์ + ชั่วโมง + วันที่เริ่ม โดยระบุชื่อลูกค้าและเบอร์โทรแบบเดียวกับการขายหน้าเคาน์เตอร์ (US-13) · ไม่ผูกกับบัญชีผู้ใช้
- [ ] ระบบสร้างการจองจริงล่วงหน้าเท่าที่หน้าต่างการจองเปิดให้ (30 วัน ⚠️ S-04) และเติมให้อัตโนมัติเมื่อหน้าต่างขยับ ทุกใบเป็นช่องทาง `Staff` และ **snapshot ราคาและนโยบายยกเลิก ณ วันที่สร้างใบนั้น** (BR-05) ไม่ใช่ ณ วันที่ตั้งชุด
- [ ] ชั่วโมงที่ถูกจองไปแล้วสร้างไม่ได้ · ระบบ **ไม่แย่งของใคร** และบอกสนามเป็นรายการว่าสัปดาห์ไหนสร้างไม่ได้เพราะอะไร ให้สนามจัดการเอง (เหมือน US-11 ตอนปิดคอร์ทแล้วมีการจองขวาง)
- [ ] แก้ชุดได้ 4 ทาง และทุกทางบันทึกเป็นประวัติ (PRD 8): **ยกเลิกเฉพาะครั้งนี้** (เข้า flow ยกเลิกของ US-13 และคิดเงินคืนตามนโยบายของใบนั้น) · **ย้ายคอร์ทเฉพาะครั้งนี้** (เข้า flow ของ US-29) · **เปลี่ยนตั้งแต่สัปดาห์หน้า** (ใบที่ยังไม่ถึงถูกสร้างใหม่ ใบที่เล่นไปแล้วไม่ถูกแตะ) · **ยกเลิกทั้งชุด** (ใบที่ยังไม่ถึงถูกยกเลิกทีละใบตามนโยบายของมันเอง)
- [ ] ชุดที่ถูกยกเลิกยังอยู่ในระบบพร้อมเหตุผลและเวลา ไม่ถูกลบ
- [ ] เงินคิดเป็นรายใบตามปกติ (US-26) **ไม่มีการเรียกเก็บรวมทั้งชุด** ⚠️ S-26

**US-31 แพ็กเกจชั่วโมง** (ขาย/ตัด: `ManageBookings` · ดูยอดคงเหลือทั้งสนาม: `ViewReports`)
ในฐานะสนาม ฉันต้องการขายชั่วโมงเป็นแพ็กเกจให้ลูกค้าประจำ เพื่อได้เงินล่วงหน้าและให้ลูกค้ามาบ่อยขึ้น
- [ ] สนามตั้ง **แบบแพ็กเกจ** ได้เอง (ชื่อ, จำนวนชั่วโมง, ราคา, อายุการใช้งานเป็นวัน) และแก้ได้โดยการเพิ่มเวอร์ชันใหม่เท่านั้น เหมือนราคาและนโยบายยกเลิก (BR-05)
- [ ] ขายแพ็กเกจให้ลูกค้าที่ระบุด้วยชื่อ + เบอร์โทร · **การขายคือเงินเข้าทันที** บันทึกเป็น `PaymentReceipt` ตามช่องทางที่จ่าย (US-26) และเข้ายอดปิดยอดของวันนั้น
- [ ] **ยอดที่ขายไปแล้วยังไม่ใช่รายได้** จนกว่าจะถูกใช้ — รายได้ของสนาม (US-15) และ GMV ของ platform (US-22) นับเมื่อชั่วโมงถูกตัดไปใช้กับการจองที่เล่นจริง ส่วนที่ยังไม่ถูกใช้แสดงเป็น **ชั่วโมงค้างส่งมอบ** แยกต่างหาก ⚠️ S-27 (ยืนยันกับนักบัญชี พร้อม Q1)
- [ ] **บัญชีชั่วโมงเพิ่มอย่างเดียว** หนึ่งแถวต่อหนึ่งการเคลื่อนไหว (ขาย +N, ใช้ −n, คืนตามนโยบาย +n, หมดอายุ −คงเหลือ) ทุกแถวบอกว่าใคร เมื่อไร และอ้างอิงการจองใบไหน · ยอดคงเหลือคือผลรวมของแถว ไม่ใช่ตัวเลขที่ถูกเขียนทับ
- [ ] ตัดชั่วโมงแทนการจ่ายเงินได้เฉพาะการจองช่องทาง `Staff` ของสนามนั้น และตัดได้ไม่เกินยอดคงเหลือ · การจองที่จ่ายด้วยแพ็กเกจมียอดค้างเป็นศูนย์และไม่มี `PaymentReceipt` เพราะเงินเข้าไปแล้วตอนขาย
- [ ] ยกเลิกการจองที่จ่ายด้วยแพ็กเกจ **คืนเป็นชั่วโมง ไม่ใช่เงิน** ตามสัดส่วนของนโยบายยกเลิก ณ ตอนจอง (BR-06) · ปัดขึ้นเป็นชั่วโมงเต็ม
- [ ] ชั่วโมงหมดอายุตามวันที่กำหนด บันทึกเป็นแถวหมดอายุ และสนามเห็นล่วงหน้าว่าของใครใกล้หมด ⚠️ S-28
- [ ] แพ็กเกจเป็นของสนามเดียว ใช้ข้ามสนามไม่ได้

### 5.6 เฟส 2 — ของที่ขายหน้าเคาน์เตอร์ และเงินที่จ่ายออก (F10, F19)

สองเรื่องนี้เป็นของคู่กัน: ลูกขนไก่ที่ขายได้คือของที่ต้องซื้อเข้ามา และสต็อกเดียวกันคือคำตอบของทั้งคู่
**บัญชีสต็อกจึงมีชุดเดียว** ฝั่งขายลบ ฝั่งซื้อบวก เหมือนบัญชีชั่วโมงของ US-31

**US-32 ขายของและเช่าอุปกรณ์หน้าเคาน์เตอร์** (ต้องมีสิทธิ์ `ManageBookings` · ตั้งรายการของ: `ManageSettings`)
ในฐานะสนาม ฉันต้องการขายลูกขนไก่ น้ำ และให้เช่าไม้ที่เคาน์เตอร์ เพื่อให้เงินส่วนนี้อยู่ในระบบเดียวกับค่าคอร์ท
- [ ] สนามตั้ง **รายการของที่ขาย** ได้เอง (ชื่อ, ราคา, หน่วย, นับสต็อกหรือไม่) · แก้โดยเอารายการเดิมออกแล้วเพิ่มใหม่เท่านั้น เหมือนราคาและแพ็กเกจ (BR-05) — บิลที่ออกไปแล้วอ้างถึงราคาที่ขายจริง
- [ ] ขายได้**ทั้งแบบผูกกับการจองและแบบขายเดี่ยว** (คนเดินเข้ามาซื้อลูกขนไก่) · หนึ่งครั้งขายได้หลายรายการ และ **ราคาเป็น snapshot ณ ตอนขาย**
- [ ] **การขายคือเงินเข้าทันที** บันทึกเป็น `PaymentReceipt` ตามช่องทางที่จ่าย (US-26) เข้ายอดปิดยอดของวันนั้น และ**ใช้วันของลิ้นชักเดียวกัน** (ปิดยอดแล้วไปอยู่วันถัดไป)
- [ ] ของที่นับสต็อก: การขาย **ตัดสต็อก** เป็นแถวในบัญชีสต็อก · ขายเกินยอดคงเหลือไม่ได้ · ของที่ไม่นับสต็อก (ค่าเช่าไม้) ขายได้เสมอ
- [ ] ยกเลิกการขาย (ทั้งใบ) **คืนของเข้าสต็อกและบันทึกการคืนเงิน** เป็นแถวใหม่ ไม่ลบของเดิม · ยกเลิกได้ครั้งเดียว
- [ ] รายงานแยก **รายได้ค่าคอร์ท** กับ **รายได้จากการขายของ** ออกจากกัน (US-15) เพราะเป็นคนละธุรกิจและอัตรากำไรคนละอย่าง · **คอมมิชชันของ platform ไม่คิดจากการขายของ** ⚠️ S-29

**US-33 ค่าใช้จ่ายและสต็อก** (บันทึก: `ManageBookings` · ดูรายงาน: `ViewReports`)
ในฐานะเจ้าของสนาม ฉันต้องการบันทึกเงินที่จ่ายออกและของที่ซื้อเข้า เพื่อรู้ว่าเดือนนี้เหลือเท่าไร
- [ ] บันทึก **ค่าใช้จ่าย** ได้: ประเภท (ของขาย / ค่าน้ำค่าไฟ / ค่าจ้าง / ค่าซ่อม / อื่น ๆ), ยอด, วันที่จ่าย, หมายเหตุ, ใครบันทึก · **เพิ่มอย่างเดียว แก้ไม่ได้** ยกเลิกได้ครั้งเดียวพร้อมเหตุผล เหมือนบันทึกการคืนเงิน (US-18)
- [ ] **ซื้อของเข้าสต็อกคือค่าใช้จ่ายหนึ่งรายการที่เพิ่มสต็อกด้วย** — เขียนทั้งสองแถวในครั้งเดียว ไม่ใช่สองหน้าจอ
- [ ] **บัญชีสต็อกเพิ่มอย่างเดียว** หนึ่งแถวต่อหนึ่งการเคลื่อนไหว (ซื้อเข้า +N, ขาย −n, คืนจากการยกเลิก +n, ปรับยอดตอนนับของ ±n พร้อมเหตุผล) · ยอดคงเหลือคือผลรวมของแถว
- [ ] **ค่าใช้จ่ายเป็นเงินสดออกจากลิ้นชัก** ถ้าจ่ายด้วยเงินสด และต้องเข้าการคิดเงินที่ควรมีตอนปิดยอด (US-26) ไม่งั้นลิ้นชักไม่มีวันตรง
- [ ] Dashboard แสดง **รายได้ − ค่าใช้จ่าย ของช่วงที่ดูอยู่** โดยบอกให้ชัดว่าไม่ใช่กำไรทางบัญชี ⚠️ S-30 (ยืนยันกับนักบัญชี พร้อม Q1)
- [ ] เตือนเมื่อของที่นับสต็อกเหลือน้อยกว่าจุดที่สนามตั้งไว้

### 6.1 State machine ของการจอง (BR-03)

```
            upload slip               staff verify              ระบบ: เวลาจบ
  [Held] ─────────────────► [PendingVerification] ──────────► [Confirmed] ─────────────► [Completed]
    │  ▲ re-upload (วนที่เดิม) │   │                             │                          │  ▲
    │                        │   │ staff reject                 │ staff: NoShow            │  │ Owner แก้
    │ ระบบ: HoldExpiresAt     │   ▼                              ▼                          ▼  │
    ▼                        │ [Rejected]                    [NoShow] ◄─── staff: NoShow ───┘  │
 [Expired]                   │                                   └──────── Owner แก้ ─────────┘
                             └──── cancel ────► [Cancelled] ◄── cancel ── (Held, Confirmed, Completed*)
```
\* `Completed → Cancelled` ทำได้เฉพาะ Owner ภายในช่วงแก้ไข

**ช่วงแก้ไข** = ตั้งแต่เวลาจบ ถึงก่อนเวลาจบ + 24 ชั่วโมง (ไม่รวมจุดสิ้นสุด)

| จาก | ไป | ใครทำ | เงื่อนไข | ยอดต้องคืน |
|---|---|---|---|---|
| — | `Held` | Booker | US-03 | — |
| — | `Confirmed` | `ManageBookings` | ช่องทาง `Staff` (US-13) | — |
| — | `Held` | `ManageBookings` | ช่องทาง `Staff` · ล็อกคอร์ทรอเงินโอนที่เคาน์เตอร์ (US-13) · หมดเวลาตาม BR-02 | — |
| `Held` | `Confirmed` | `ManageBookings` | ช่องทาง `Staff` เท่านั้น · เงินเข้าแล้ว · ก่อน `HoldExpiresAt` | — |
| `Held` | `PendingVerification` | Booker อัปโหลดสลิป | เวลา server < `HoldExpiresAt` (ตรวจใน transaction เดียวกัน) | — |
| `Held` | `Expired` | ระบบ | ถึง `HoldExpiresAt` · ถ้าผู้จองโอนแล้วแต่อัปโหลดไม่ทัน ให้ติดต่อสนาม สนามคืนเงินนอกระบบ หรือสร้างการจองช่องทาง `Staff` ให้ถ้าช่องยังว่าง | 0 |
| `Held` | `Cancelled` | Booker หรือ `ManageBookings` | ก่อน `HoldExpiresAt` · ไม่ต้องระบุเหตุผล | 0 |
| `PendingVerification` | `PendingVerification` | Booker เปลี่ยนสลิป | US-04 | — |
| `PendingVerification` | `Confirmed` | `VerifySlip` | ถ้าเลยเวลาจบไปแล้ว ระบบเปลี่ยนเป็น `Completed` ต่อทันที | — |
| `PendingVerification` | `Rejected` | `VerifySlip` | ต้องระบุเหตุผล · ช่องเวลากลับมาว่าง | "ได้รับเงินจริง" = 100% · "ไม่ได้รับเงิน" = 0 |
| `PendingVerification` | `Cancelled` | Booker (ก่อนเวลาเริ่มเล่น) | สถานะการรับเงินเป็น `Unconfirmed` จนกว่า `ManageBookings` จะเลือก ได้รับ / ไม่ได้รับ (US-13) | ได้รับ = 100% · ไม่ได้รับ = 0 · ระหว่างรอ = 0 และอยู่ในรายการที่ต้องจัดการ (US-15) |
| `PendingVerification` | `Cancelled` | `ManageBookings` | ต้องเลือกว่าได้รับเงินหรือไม่ | ได้รับ = 100% · ไม่ได้รับ = 0 |
| `PendingVerification` | (ค้างอยู่) | — | **ไม่มีหมดเวลาอัตโนมัติ** ช่องเวลายังถูกกันไว้เพื่อคุ้มครองผู้จองที่โอนแล้ว และระบบเตือนตาม US-17 | — |
| `Confirmed` | `Cancelled` | Booker (ก่อนเวลาเริ่มเล่น) | | ตามนโยบาย snapshot นับชั่วโมงจากเวลาที่กดยกเลิกถึงเวลาเริ่มเล่น |
| `Confirmed` | `Cancelled` | `ManageBookings` (ก่อนเวลาจบ) | ต้องเลือกเหตุผล | `CustomerRequest` = ตามนโยบาย snapshot นับชั่วโมงจากเวลาที่กดยกเลิกถึงเวลาเริ่มเล่น (ถ้าเลยเวลาเริ่มแล้ว = 0%) · `VenueInitiated` = 100% · `PaymentNotReceived` = 0 |
| `Confirmed` | `NoShow` | `ManageBookings` | ตั้งแต่เวลาเริ่มเล่น + 15 นาที ถึงเวลาจบ · ช่องเวลาที่เหลือกลับมาว่าง | 0 |
| `Confirmed` | `Completed` | ระบบ | ถึงเวลาจบ · ทุก query ถือว่า `Confirmed` ที่เวลาจบ ≤ now เป็น `Completed` แม้ job ยังไม่รัน (9.2) | — |
| `Completed` | `NoShow` | `ManageBookings` | ภายในช่วงแก้ไข | 0 |
| `NoShow` | `Completed` | Owner | ภายในช่วงแก้ไข · ต้องระบุเหตุผล · **ทำไม่ได้ถ้ามีการจอง active ทับช่วงเวลาเดิม** | — |
| `Completed` | `Cancelled` | Owner | ภายในช่วงแก้ไข · เหตุผล `PaymentNotReceived` (เช่น เพิ่งพบว่าสลิปปลอม) หรือ `VenueInitiated` | `PaymentNotReceived` = 0 · `VenueInitiated` = 100% |

**กฎทั่วไปของ state machine**
- การต่อเวลาและการย้ายคอร์ท (US-29) **ไม่อยู่ในตารางนี้** เพราะไม่เปลี่ยนสถานะ — มันเปลี่ยนชั่วโมงที่การจองถืออยู่ และถูกบันทึกแยกต่างหาก
- `Expired`, `Rejected`, `Cancelled` เป็นสถานะสุดท้าย ส่วน `Completed` และ `NoShow` เป็นสถานะสุดท้ายเมื่อพ้นช่วงแก้ไข
- ผู้จองที่ถูกปฏิเสธต้องสร้างการจองใหม่
- **ห้ามเปลี่ยนจาก `Confirmed` เป็น `Rejected`** ถ้ายืนยันผิด ให้ยกเลิกด้วยเหตุผลที่ตรงกับกรณีแทน

## 9. แนวทางทางเทคนิค

### 9.1 Architecture
```
Angular SPA (PWA) ──HTTPS──► Caddy ──/api──► ASP.NET Core Web API ──EF Core──► PostgreSQL
                                        │
                                        ├── S3-compatible storage นอกเครื่อง (สลิป, หลักฐานการคืนเงิน/ชำระ, PDF, backup)
                                        ├── Scheduled jobs (Expired, Completed, เตือนก่อนเล่น, สลิปค้างตรวจ, คอมมิชชันวันที่ 2)
                                        ├── Email service
                                        └── LINE Login (MVP) · LINE Messaging API/LIFF (เฟส 2)
```

### 9.2 ประเด็นทางเทคนิคสำคัญ
- **Multi-tenant:** ใช้ database เดียวร่วมกัน ตารางของสนามมี `VenueId` · บังคับด้วย EF Core global query filter + authorization policy ที่ตรวจทั้ง "สนามที่กำลังจัดการ" และสิทธิ์ (US-14)
- **กันจองซ้อน (BR-04):** PostgreSQL exclusion constraint บน `(court_id, tstzrange(start, end))` ของตาราง BookingSlot สำหรับแถวที่ `is_active = true`
  - ทุกการเปลี่ยนสถานะที่กระทบ active ต้องอัปเดต `is_active` ใน transaction เดียวกัน
  - ถ้า `NoShow → Completed` ชน constraint ให้ตอบ error ที่อ่านเข้าใจได้ (6.1)
- **Held ที่หมดเวลา:** ต้องไม่พึ่ง scheduled job อย่างเดียว เพราะ job อาจช้าหรือ container อาจ restart (R3)
  - ทุก query ที่ตรวจความว่าง และตอนสร้างการจองใหม่ ถือว่า `Held` ที่ `HoldExpiresAt < now` ไม่ active และปล่อยช่องนั้นใน transaction
  - job ยังคงทำหน้าที่เปลี่ยนสถานะเป็น `Expired` ภายหลัง
- **Confirmed ที่เลยเวลาจบ:** ทุก query และทุกการตรวจเงื่อนไขในหัวข้อ 6.1 ถือว่าเป็น `Completed` ทันที แม้ job ยังไม่รัน
- **Scheduled jobs:** ใช้ hosted service ใน container ของ API (เครื่องเปิดตลอด) · ทุก job ต้อง idempotent (รันซ้ำได้โดยไม่เกิดผลซ้ำ) · ถ้า container restart ต้องตามทำงานที่ค้างได้ · job คอมมิชชันต้องไม่นับการจองซ้ำข้ามใบแจ้งหนี้ · ทุก job ส่ง heartbeat ไปที่ uptime monitor (9.3)
- **QR PromptPay:** server สร้าง payload ตามมาตรฐาน EMVCo QR พร้อมยอดเงิน
- **เลขที่เอกสาร:** ใช้ตาราง counter ที่ล็อกแถวใน transaction เดียวกับการสร้างเอกสาร (ไม่ใช้ sequence ของ database เพราะ sequence ข้ามเลขได้)
- **PDF:** เลือก library ใน M1 โดยต้องตรวจ license ว่าใช้เชิงพาณิชย์ได้ฟรี · **ต้อง embed ฟอนต์ไทย** (เช่น Sarabun หรือ Noto Sans Thai) ไว้ในโปรเจกต์ เพราะ Linux ไม่มีฟอนต์ไทยติดมา
- **.NET บน Linux:**
  - ใช้ image `mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled-extra` ซึ่งมี ICU + tzdata ห้ามใช้ image ที่ไม่มี เพราะ `Asia/Bangkok` (BR-10) และ culture ไทยจะทำงานผิด
  - build image แบบ multi-arch `linux/amd64,linux/arm64` (UAT เป็น ARM)
  - ใช้ `.gitattributes` บังคับ LF สำหรับ shell script และไฟล์ config
  - ระวังชื่อไฟล์และ path แยกตัวพิมพ์เล็ก-ใหญ่ (CI รันบน Linux จึงจับได้)
